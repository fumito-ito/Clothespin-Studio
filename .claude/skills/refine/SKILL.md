# Issue リファインメント: $ARGUMENTS

`$ARGUMENTS` は Issue 番号。判断業務なので上位モデルが実施する（スパイクの実行のみ委任可）。
INVEST / SPIDR / アジャイルスパイクの標準プラクティスを AI 委任向けに翻案したもの。

## 1. 精査 — 委任可能性の判定（INVEST 翻案）

Issue を読み、次をすべて満たすか判定する。満たすなら「そのまま委任可能」と報告して終了。

- [ ] **Small**: 1 セッション・1 PR で完結する（目安: 変更 2〜5 ファイル、受入基準 2〜4 個）
- [ ] **Testable**: 受入基準がすべて機械検証可能（テスト名・コマンド・数値で判定できる）
- [ ] **Independent**: `depends:` 以外の進行中作業と衝突しない
- [ ] **自己完結**: 対象ファイル・触るインターフェース・**スコープ外**が明記されている
- [ ] **不確実性なし**: 未決の設計判断・実現可能性が不明なアルゴリズム・未調査の外部仕様が残っていない

1 つでも欠けたら §2（不確実性がある場合）→ §3（分割）へ。

## 2. スパイク — 不確実性の解消（分割より先に行う）

「どう分割すべきかすら分からない」原因は大抵ここ。以下の規律で仮説検証する:

1. **問いを 1 文で書く**（曖昧なテーマは不可）。
   例: 「非 watertight メッシュでもレイキャスト内外判定は破綻しないか？」
2. **このスパイクが可能にする決定と、ブロックを解除する Issue を先に名指しする**
   （それが書けないスパイクはやらない）
3. **成功基準と成果物を先に決める**: 判定record・計測値・プロトタイプのどれで「答えた」とするか。
   例: 「穴あきメッシュ 3 種で誤判定率を計測し、方式 A/B のどちらを採るか決める」
4. **タイムボックス = ターン上限**（例: 10 ターン）。超過したら延長せず、分かったことを記録し、
   より狭い問いの後続スパイクに切り直す
5. **仮実装は捨てる前提**。scratchpad か `spike/` ブランチに書き、本体にマージしない。
   残す判断をした場合のみ通常の品質基準（テスト・lint）を適用し直す
6. **結果は Issue に書き戻す**: 答え・採用方式・計測値・残リスクを「参照」節に追記
7. 問い・成功基準・ターン上限が明文化できたら、**スパイクの実行自体は implementer に委任してよい**

## 3. 分割 — SPIDR 翻案（薄い縦切りで）

各子 Issue が**単独で検証可能**になるように、以下のパターンを優先順に検討する:

| パターン | 例（本リポジトリ） |
| --- | --- |
| **Paths（工程/経路）** | パイプラインの工程ごと: 読込 → 正規化 → ボクセル化 → 色割当 |
| **Interfaces（入口を絞る）** | まず GLB だけ通す。STL / OBJ は後続 Issue に |
| **Data（データを絞る）** | まず watertight・単色モデルのみ対応。穴あき・多色は後続に |
| **Rules（ルールを緩める）** | まず粗い方式（低解像度・単純判定）で通し、精度向上を別 Issue に |
| **Spike の切り出し** | §2 の問いをスパイク Issue として先行させる |

分割の規律:

- **横切り（層だけの分割）は避ける**。ただし `src/domain/` は vitest 単体で検証可能なので、
  「ドメインロジック（テストで完結）」と「UI 配線（プレビューで確認）」の 2 分割は縦切りとみなしてよい
- 子 Issue は新規ファイル（次の連番で採番）+ frontmatter に `parent: <元番号>`。`depends:` を正しく張る
- **各子 Issue は §1 のチェックを満たすまで書き込む**（対象ファイル・受入基準・スコープ外・参照）
- 子 Issue に**モデル選定の目安**（haiku / sonnet / opus）を 1 行書く
- 元 Issue は本文を「分割済み」概要 + 子 Issue 一覧に置き換える。全子完了で `status: done`

## 4. 報告とコミット

子 Issue 一覧（番号・タイトル・依存・モデル目安）とスパイクの結論を要約して報告し、
docs/issues/ の変更をコミットする。
