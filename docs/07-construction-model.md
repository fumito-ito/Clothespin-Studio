# 07. 立体構築モデルの調査と設計（ルールベース生成アセンブリ）

> ステータス: 方針確定＝**既存3Dモデルの取り込み → クリップ近似（単一路線・クライアント完結）**
> （統合ブランチ `develop/generate-from-image`）。次の着手は M1（取り込み→ボクセル化）。
> 「**組み立て可能な**立体をクロソピンで近似する」ための構築モデルを定める。
> 構築玩具を調査して成長パラダイムを確定し（§1–§6）、ゴールを取り込み路線に一本化して
> ロードマップを定めた（§7–§9）。レリーフ（画像→2.5D）と画像からの ML 復元は不採用（§7/§8）。

## 1. 背景と問題

[06](06-generate-from-image.md) のレリーフ生成は **各タワーが独立（フォレスト）** で、相互に連結
していない＝1 つの組み立て可能体になっていない。連結しようとすると、クロソピンの連結幾何の制約に
ぶつかる（実測で確定）:

- **回転 0 の単一連結は存在しない**。最小でも 1 リンクあたり 31°（`g1`）回転し、z 方向にもズレる。
- → 連結チェーンは必ず曲がる/浮く。**規則正しい平面格子も垂直タワー列もタイル状に敷けない**。
- period-2（2 連結）で回転を打ち消す「直線ユニット」は作れる（例 `g4/g6` 系で `(-40,±30,±10)`）が、
  素朴に格子化すると **自己干渉（試作 36/49）・非平面（厚み 119mm）** になった。

結論として、**「格子に置く」発想ではクロソピンの立体は作れない**。専用の構築モデルが要る。

## 2. 調査：類似玩具・手法の構築モデル

| 玩具/手法 | モデル | クロソピンへの適合 |
| --- | --- | --- |
| **LEGO**（BrickLink Studio / legolization） | ボクセル化 → 層ごとにブロック充填 + 連結/安定性解析（GA・力解析） | ✗ **規則格子に乗るコネクタ前提**。クロソピンは格子に乗らない |
| **ハブ-ストラット**（Zometool / K'NEX / Posey） | ノード（多方向ソケット）＋ストラットのグラフ。角度は**ハブ**が規定 | △ クロソピンは「クランプ付きストラット」だが**専用ハブが無く**、角度がクリップに焼き込まれている |
| **磁性パネル**（Magformers） | 多角形ネットを辺で連結 → 折って多面体 | ✗ 面要素前提。クロソピンは線/クリップ要素 |
| **インターロッキング・アセンブリ / シェイプ・グラマー** | **離散要素の言語＋連結ルール**で形を創発させ、目標形状にフィット | ◎ **クロソピンに最も合うパラダイム** |

出典は §8。

## 3. 結論：採用パラダイム

**ルールベース生成アセンブリ（シェイプ・グラマー / インターロッキング・アセンブリ）** を採用する。

理由: クロソピンは **向きを持つクリップ・コネクタ**で、連結が **有限のルール集合（catalog）** で
記述でき、格子に乗らない。したがって「格子に置く」のではなく「**ルールで成長させて目標形状を
近似する**」のが本質的に正しい。LEGO の貢献は「**目標のボクセル化**」だけ借用する。

## 4. 提案モデル

### 4.1 連結カタログ（= 文法の語彙）
- 有効な `(socket, roll, pitch) → 相対変換（親ローカル）` の有限集合。
- すでに `domain/solve.ts` の `childWorldMatrix` で計算可能（[06](06-generate-from-image.md) の period-2 探索が実例）。
- 各エントリは「子の相対位置・相対回転・占有ソケット」を持つ。これが文法の生成規則。

### 4.2 目標表現（target）
- 望む形を **ボクセル化**する（画像→高さ場、または 3D モデル→ボクセル）。
- ボクセルの一辺 ≒ ピンの代表寸法/間隔。各ボクセルに「色（最近傍パレット）」を持たせる。

### 4.3 生成：幅優先（BFS）で連結木を成長
1. 種ピン（1 本）を目標内に置く。
2. 幅優先で各ピンを 1 回ずつ展開し、未占有ソケットごとにカタログ順で子候補を試行する。
3. 候補が (a) 未充填の目標ボクセルに入る、(b) 既存ピンと干渉しない（`domain/collision.ts` の OBB×SAT）を満たす場合に採用する。
4. 目標を覆う or 有効手が尽きるまで反復する（連結は常に木構造で保たれる）。

### 4.4 制約・評価
- **連結**: 木（フォレスト→単一ルート）で保証。
- **干渉**: 既存の干渉判定をハード制約に。
- **安定性**（将来）: LEGO 研究の力解析を参考に、自重で倒れない/接合が持つかを後段で評価。
- **被覆率**: `覆えた目標ボクセル / 全目標ボクセル`。これが品質指標。

データモデル（[03](03-data-model.md)）は変更不要。生成結果は通常のピン木。

## 6. 限界・未知数（正直な見立て）

- インターロッキング系は研究でも「**組み立て方向に制約**」があるとされ、**カタログが届かない領域は
  カバーできず近似**になる。完全再現は保証されない。
- カタログの相対変換は離散・固定なので、**目標ボクセルに綺麗に整列するとは限らない**（成長が逸れる）。
- よって「どこまで似せられるか」は**被覆率を実測**して見極めるのが先決（§7）。

## 7. ゴールの確定：既存3Dモデルの取り込み → クリップ近似（単一路線）

経緯（レリーフ、生成的 image-to-3D）を検討した結論として、機能を**単一路線**に絞る:

> **既存の 3D モデル（GLB / STL / OBJ）を取り込み、ボクセル化して `growAssembly` で
> 連結クリップ集合に近似する。**

```
既存3Dモデル(GLB/STL/OBJ) → three.js ロード → 正規化(スケール/向き/単位)
→ ボクセル化(内外判定; ソリッド or シェル) → 最近傍パレット色 → growAssembly(既存) → 連結クリップ集合
```

**理由:**
- この app の新規価値は **「クリップでの立体近似」** であって 3D 復元ではない。欲しい形の 3D モデル
  （キャラクター等）は世の中に既に存在し、ダウンロードできる。**復元する必要がない。**
- 取り込み路線は **NFR-10（クライアント完結・外部送信なし）を守れる**。three.js でブラウザ内に
  モデルを読み込み、ボクセル化も純 TS で完結。**サーバ・ML・GPU 課金は不要。**
- 下流（成長・干渉・部品表・エクスポート）は既存資産をそのまま共有。違いは
  **「目標ボクセルをどう得るか」だけ**で、それが「画像の高さ場」から「3D モデルのボクセル化」に変わる。

**入力の性質の変化（明示）:** 「どんな写真でも」→「ユーザーが 3D モデルを用意する」。対象がホビイスト
（欲しいキャラのモデルは入手できる）なら妥当。生成物の著作権/ライセンスはユーザー持ち込み素材の責任
（app は画像持ち込みと同じ扱い）。

**不採用（スコープ外・記録のみ）:**
- **レリーフ（画像→2.5D）**: 上から絵・横から起伏の“板”で原理的に立体でない（裏面が無い）。実装は削除。
- **生成的 image-to-3D（画像から ML 復元）**: 採らない。理由は §8。

## 8. 不採用の記録：なぜ画像から ML 復元（案A）を採らないか

「1 枚の画像から立体」を復元する本命は生成的 image-to-3D（TripoSR / InstantMesh / TRELLIS /
Hunyuan3D、または Meshy / Tripo / Rodin 等の商用 API）だが、以下の理由で**採用しない**。
そもそも **欲しい 3D モデルは既に存在し、取り込めば復元自体が不要**、というのが決め手。

1. **NFR-10 との正面衝突【決定打】** — 生成モデルは GPU（数 GB VRAM）・PyTorch/CUDA 前提でブラウザ
   完結不可。サーバ GPU か商用 API が必須 → **どちらも「外部送信なし」を破る**。取り込み路線はこれを回避。
2. **運用コスト・依存** — ML 推論スタック（重み数 GB・GPU・背景除去/正規化の前処理）or 従量課金 API・
   第三者依存。純クライアント（GitHub Pages 配信）から大きく逸脱。
3. **品質の不確実性** — 単画像復元は**裏面をハルシネーション**。翼膜・角・爪など**薄板/突起は融合・欠落**、
   **炎（半透明・発光）は形として復元不能**。最も特徴的な部位ほど壊れる。
4. **非決定性** — 実行ごとに違うメッシュ → 同一入力でも結果がばらつき、部品表/作り方の再現・共有に影響。

> **注意（この路線を外しても消えないリスク）**: 最深リスク＝**「実形状（凹み・薄壁・オーバーハング）を
> 良い被覆率でクリップ近似できるか」は入力に依らず存在する**（画像でも 3D モデルでも同じ）。現状の
> 被覆率 100% は板/球/L字など凸寄り・単純形状での実測にすぎない。取り込み路線の利点は、この核心リスクを
> **ML のブラックボックス越しでなく、良質な既知モデルで直接・早期に検証できる**こと（→ M2）。

## 9. ロードマップ（単一路線）

- **M1. 3D モデル取り込み → ボクセル化** — ⬜ **次の着手点**。three.js の `GLTFLoader`/`STLLoader`/
  `OBJLoader` でブラウザ内ロード → 正規化（スケール/向き/単位）→ ソリッド/シェル ボクセル化
  （`"i,j,k"`→最近傍パレット色）。受入: 代表モデルをボクセル表示でき、色が付く。
- **M2. 成長でクリップ近似【核心リスクの検証】** — ⬜ **最重要**。ボクセル目標を既存 `growAssembly` に
  接続し、**実形状（凹み・薄壁・オーバーハング）での被覆率・単一連結・干渉 0 を実測**。ここが製品の成否。
  受入: 代表モデルで被覆率 ○%・自立・干渉 0。
- **M3. スケール/ピン数の実用化** — ⬜。中空化（シェル）・LOD・ボクセルサイズ調整で `PIN_LIMIT`(20000)
  以内に収める。受入: 実サイズ（例 40–80cm）で上限内・破綻なし。
- **M4. パレット拡張と色マッピング** — ⬜。現状 3 色（blue/white/warmgray）→ 実用色数へ拡張。
  モデル色 → パレット量子化の質を上げる。
- **M5. 被覆品質の底上げ** — ⬜。未充填ボクセルのリペアパス・種選択（M2 で被覆率が落ちる領域向け）。
- **M6. 物理的安定性・組み立て可能性** — ⬜。自重・接合強度・接地・組立手順書（§4.4 の力解析）。
- **M7. 統合 UX / エクスポート / クリーンアップ** — ⬜。取り込みダイアログ、既存の部品表/GLB/STL/PNG
  エクスポートとの統合、**旧レリーフ実装の削除**、docs 更新。

**依存**: M1 → M2 →（M3 / M4 / M5）→ M6 → M7。**M2 が最重要**（核心リスク）。

### クリーンアップ（削除対象・M7 で実施 or 先行）
レリーフ（画像→2.5D）は不採用のため、以下を削除して取り込み UI に置換する:
- `ui/GeneratorDialog.tsx` の画像/高さ場まわり、`io/imageToCells.ts` と `io/imageToCells.test.ts`
- `domain/generator.ts` の `luminance`/`luminanceToHeight`/`nearestColorId`/`cellsToVoxels`
  （色量子化・最近傍パレットは取り込みでも使うので **一部は移設して流用**）
- `i18n/messages.ts` の `gen*` 文言、`state/store.ts` の合成画像デバッグヘルパー

**流用（そのまま活用）**: `domain/grow.ts`（成長）/ `domain/catalog.ts`（連結カタログ 133 手）/
`domain/collision.ts`（OBB×SAT）/ `domain/graph.ts`（連結整合性）/ 部品表・各エクスポート。
データモデル（[03](03-data-model.md)）は変更不要。

### 実装メモ
- 立方ボクセル一辺は既定 `45mm`（被覆率実測で好結果。定数の所在は取り込み UI 側へ移す）。
- 連結は木構造で保証、干渉は OBB×SAT をハード制約に（既存 `collision.ts` 流用）。
